# 2.4 — Building on Arbitrum (EVM)

> **TL;DR:** Arbitrum is **EVM-equivalent**, so your Solidity, Foundry, Hardhat, viem/wagmi all work unchanged — you just point them at Arbitrum's RPC. Two things differ from L1: **gas is two-dimensional** (L2 execution + the L1 cost of posting your calldata), and there are **Arbitrum-specific precompiles** (`ArbSys`, `ArbGasInfo`, `NodeInterface`) for L2 features. **Timeboost** is Arbitrum's ordering policy that auctions a short "express lane" instead of running latency races.

Same JSON-RPC as Ethereum — any EVM tool works by swapping the RPC URL and chain ID.

## Gas on Arbitrum (two-dimensional)

A tx fee on Arbitrum is the **sum of two parts**:

1. **L2 execution** — the compute you use, at the current L2 gas price. Usually **cheap**.
2. **L1 data posting** — the cost the sequencer pays to post your (compressed) tx as calldata/blobs on Ethereum. Usually the **dominant** cost.

```
fee ≈ L2gasPrice × (L2gasUsed  +  (L1pricePerByte × compressedSize) / L2gasPrice)
```

Both are bundled into one number the user sees. **Key takeaway:** on L2 the bottleneck is **calldata size**, not computation — the same reason smaller calldata / blobs matter. To estimate correctly, don't use plain `eth_estimateGas`; call **`NodeInterface.gasEstimateComponents()`** (or `gasEstimateL1Component()`), which returns both parts so you can separate L1 posting from L2 execution.

## Precompiles

Special contracts at fixed addresses that expose L2-only functionality:

| Precompile | Address | What it's for |
|---|---|---|
| **ArbSys** | `0x64` | System stuff: **L2→L1 messaging** (`sendTxToL1`), `arbBlockNumber` |
| **ArbGasInfo** | `0x6c` | Live **gas price components** (L1 base fee estimate, per-byte price, backlog) |
| **ArbRetryableTx** | `0x6e` | Create/redeem **retryable tickets** (L1→L2 messages) |
| **ArbAddressTable** | `0x66` | Register addresses to **compress calldata** and save on L1 cost |
| **NodeInterface** | *(pseudo)* | **Gas estimation** + building **outbox proofs**. Not a real deployed address — a virtual helper the node exposes. |

## Deploy a Solidity Contract to Arbitrum Sepolia

Because it's EVM-equivalent, deploying is the **same flow as any EVM chain** — just target the Arbitrum Sepolia RPC (chain `421614`):

- **Foundry:** `forge create src/MyContract.sol:MyContract --rpc-url https://sepolia-rollup.arbitrum.io/rpc --private-key $PK --broadcast` (add `--verify` with an Arbiscan key).
- **Hardhat:** add the `arbitrumSepolia` network in `hardhat.config.ts` and run your deploy script `--network arbitrumSepolia`.
- Get testnet ETH: bridge Sepolia L1 ETH via [bridge.arbitrum.io](https://bridge.arbitrum.io), or use an Arbitrum Sepolia faucet.
- Verify on `sepolia.arbiscan.io`. Your contract code doesn't change at all — only the endpoint does.

## Timeboost & the Express-Lane Model

**Timeboost** is Arbitrum's transaction-ordering policy for capturing MEV in a controlled way instead of via latency races.

- **The problem it replaces:** first-come-first-served ordering rewards whoever has the fastest connection → spam and expensive latency wars.
- **The auction:** every round (default **60s**) there's a **sealed-bid, second-price auction** for control of an **express lane**. The winner's txs are sequenced **immediately**, while everyone else's get a small (~200ms) delay.
- **Limits:** the winner **can't reorder** other txs or guarantee profit — they just get a brief time edge. The mempool stays private (protects against front-running).
- **Proceeds:** the auction revenue (second-highest bid) goes to a **beneficiary set by the chain owner** — a new revenue stream for the chain.
- **Normal txs still work fine** — they just take a ~200ms-longer path to sequencing; block times stay ~250ms.

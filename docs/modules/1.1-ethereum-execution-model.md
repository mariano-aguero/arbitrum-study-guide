# 1.1 — Ethereum Execution Model

> **TL;DR:** Ethereum is a replicated state machine. Accounts hold state, signed transactions mutate it, the EVM executes them deterministically, gas puts a price on every step, and events/logs are how you read what happened.

## State, Blocks & Finality

- Ethereum is a **world computer**: one global state (all accounts + balances + contract storage) replicated across every node.
- A **transaction** is the only thing that changes state. A **block** is an ordered batch of transactions; applying it moves the chain from state *N* to state *N+1*.
- **Finality**: a block is *finalized* (~2 epochs, ≈13 min) when it can't be reverted without burning ≥1/3 of staked ETH. Before that it's just "included".

## Accounts: EOA vs Contract

|  | EOA | Contract |
|---|---|---|
| Controlled by | Private key | Its own code |
| Can initiate a tx | ✅ Yes (only EOAs can) | ❌ Only reacts to calls |
| Creation cost | Free | Costs gas (stores code) |

Every account has 4 fields: **nonce** (tx counter, prevents replays), **balance** (in wei), **codeHash** (empty for EOAs), **storageRoot** (hash of its persistent storage).

**Transactions** are signed with the EOA's private key (ECDSA). The signature proves authorship without revealing the key; the **nonce** forces strict ordering and blocks replay attacks.

## EVM: A Deterministic State Machine

Same bytecode + same input + same state = **same result on every node**. That's what makes global consensus possible.

Where data lives during execution:

| Location | What it is | Cost |
|---|---|---|
| **Stack** | LIFO, max 1,024 slots of 32 bytes — where opcodes operate | Cheapest |
| **Memory** | Volatile scratch space, wiped after the tx | Cheap (grows quadratically) |
| **Storage** | Persistent key→value (256-bit → 256-bit), part of world state | Most expensive (`SSTORE`) |
| **Calldata** | Read-only tx input: 4-byte function selector + ABI-encoded args | Cheap to read |

- Contracts are compiled to **bytecode**; the EVM executes it opcode by opcode (`ADD`, `MLOAD`, `SSTORE`, `CALL`, …) via a program counter.
- Explore and step through any opcode interactively at [evm.codes](https://www.evm.codes/).

## Gas: Pricing Computation

- **Gas** = unit of computational work. Every opcode has a cost; a plain ETH transfer costs **21,000 gas**. It exists to prevent spam and infinite loops.
- **Gas limit** = max gas you allow the tx to consume. Unused gas is refunded; running out reverts the tx (but you still pay for what ran).
- **EIP-1559** fee model:
  - **Base fee** — set by the protocol per block, adjusts ±12.5% max with demand, and is **burned**.
  - **Priority fee (tip)** — goes to the validator to get you included faster.
  - **Max fee** — your ceiling; you pay `gas used × (base fee + priority fee)` and the difference is refunded.
- Prices are quoted in **gwei** (10⁻⁹ ETH). Example: 21,000 × (10 + 2) gwei = 0.000252 ETH.

## Events, Logs & the Read-Side

- Contracts can't return data to the outside world on their own — they **emit events**, which are written as **logs** in the tx receipt.
- Logs are **cheap** (much cheaper than storage) but **contracts cannot read them** — they exist only for off-chain consumers.
- Indexed event parameters become **topics**, which apps filter on (e.g. "all `Transfer` events to my address").
- The read-side model: dapps and indexers (viem `watchEvent`, The Graph, etc.) reconstruct application state by listening to logs instead of querying storage — reads via `eth_call` are free and don't create transactions.

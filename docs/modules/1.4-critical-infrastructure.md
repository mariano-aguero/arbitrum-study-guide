# 1.4 — Critical Infrastructure

> **TL;DR:** Contracts can't reach the outside world on their own. Oracles (Chainlink) bring data in, indexers (The Graph) make on-chain data queryable, IPFS/Arweave store what's too big for the chain, OpenZeppelin gives you audited building blocks, and block explorers are your first debugging tool.

## Oracles: Chainlink

Blockchains are deterministic and isolated — they can't fetch a price or an API result. **Oracles** bridge that gap; Chainlink is the dominant one:

- **Data Feeds** — decentralized price feeds (many independent nodes → one aggregated on-chain answer). The consumer pattern:

```solidity
AggregatorV3Interface feed = AggregatorV3Interface(FEED_ADDRESS);
(, int256 answer,,,) = feed.latestRoundData();   // e.g. 3030914000000
```

  ⚠️ Answers are integers with **per-feed decimals** (BTC/USD has 8 → that's $30,309.14). On L2s, also check the **Sequencer Uptime Feed** — a downed sequencer means stale prices.
- **VRF** — verifiable on-chain randomness (lotteries, NFT mints). Never use `block.timestamp` for randomness.
- **Automation** — decentralized cron: calls your contract when a condition/schedule triggers.
- **CCIP** — cross-chain messaging and token transfers between networks.

## Indexing: The Graph (& friends)

Querying "all Transfers for this address" via raw RPC is brutally slow — **indexers** listen to events and serve them as fast queryable APIs.

- **The Graph** — define a **subgraph** with 3 files:
  1. `subgraph.yaml` (manifest) — which contract, which events, from which `startBlock`
  2. `schema.graphql` — the entities you want to store
  3. `src/mapping.ts` — handlers: event in → entity out (`entity.save()`)

  Then `graph codegen && graph build`, deploy, and query it with **GraphQL** (filtering, ordering, pagination for free).
- **Alternatives:** **Subsquid** (high-throughput SDK-based indexing) and **Ponder** (TypeScript-first, local-friendly — think "Drizzle for events"). Same idea, different DX.

## Storage & Data Availability: IPFS & Arweave

On-chain bytes are expensive — store big content off-chain, keep only a reference on-chain.

- **IPFS** — content-addressed storage: a file's address is the hash of its content (**CID**). Change the file → different CID, so links are tamper-evident. Files persist only while someone **pins** them (Pinata, web3.storage).
- **Arweave** — pay once, stored ~forever (endowment model). Common for NFT assets that must outlive any pinning service.
- Typical NFT pattern: image + JSON metadata on IPFS/Arweave, the contract's `tokenURI` just points at it (`ipfs://<CID>`).

## Smart-Contract Libraries: OpenZeppelin

Already covered in [1.2](/modules/1.2-solidity-abi-contract-lifecycle) — the audited standard library: ERC implementations, `Ownable`/`AccessControl`, `ReentrancyGuard`, upgrade tooling. Default to it; write from scratch only when you have a reason.

## Block Explorers as Debugging Tools

**Etherscan** is often the fastest way to answer "what did this tx actually do?":

- **Tx page** — Status, gas used vs limit, value. *Failed txs still consume gas.*
- **Input Data** — the calldata: 4-byte selector + args, auto-decoded if the contract is verified.
- **Logs tab** — emitted events: Topic 0 = event signature hash, Topics 1–3 = indexed params, Data = the rest.
- **Internal Txns** — contract-to-contract sub-calls (not separate txs) — trace where the ETH/execution actually went.
- **Read/Write Contract tabs** — poke any verified contract without writing a line of code.
- **Token Transfers tab** — ERC-20 movements and approvals (spot unauthorized allowances).

**Otterscan** — open-source, local-first explorer that pairs with your own node/anvil — same workflow, no third party.

# 2.3 — Cross-chain Messaging & Bridges

> **TL;DR:** L1 and L2 talk through an **Inbox** (messages going down, L1→L2) and an **Outbox** (messages coming up, L2→L1). Going down uses **retryable tickets** — an L1 tx that guarantees eventual L2 execution. Going up uses **ArbSys.sendTxToL1** and is subject to the **challenge period (~7 days)** before you can claim on L1. The **token bridge** is built on this: deposits lock on L1 and mint on L2; withdrawals burn on L2 and release on L1 after the delay.

## Inbox / Outbox Model (parent ↔ child)

- **Inbox** (on L1) — the entry point for **parent → child** messages. Anything going from Ethereum down to Arbitrum passes through it (deposits, contract calls, force-included txs).
- **Outbox** (on L1) — the exit point for **child → parent** messages. L2→L1 messages land here and are claimed after they're confirmed.
- **Address aliasing** — when an **L1 contract** sends a message to L2, the L2 sees an *aliased* address (`L1address + 0x1111…1111`), not the original. This stops an L1 contract from impersonating the same address on L2. EOAs (signed txs) aren't aliased. Use `AddressAliasHelper` when your L2 contract needs the real L1 sender.

## Retryable Tickets, ArbSys & the Withdrawal Flow

**L1 → L2: retryable tickets.** The canonical way to send a message down.
- You call `createRetryableTicket` on the Inbox; it produces a **TicketID** and guarantees the message will *eventually* execute on L2.
- **Submission + execution are decoupled.** You pay a **submission fee** (based on calldata size) on L1, plus L2 gas.
- **Auto-redeem:** if you funded enough L2 gas, it executes automatically within minutes.
- **Manual redeem:** if auto-redeem fails (e.g. gas spiked), *anyone* can redeem it later via the `ArbRetryableTx` precompile.
- **Expiry:** the ticket stays redeemable for **~7 days**; after that the value is refunded to the beneficiary.

**L2 → L1: ArbSys + the two-step withdrawal.**
1. An L2 contract calls **`ArbSys.sendTxToL1`** — this queues an L2→L1 message.
2. You **wait out the challenge period (~7 days)** — the message can't be trusted on L1 until the assertion containing it is confirmed (this is the optimistic-rollup delay from [2.2](/modules/2.2-fraud-proofs-and-bold)).
3. After confirmation you **execute it on L1**: build the proof (`NodeInterface.constructOutboxProof`) and call the **Outbox's** `executeTransaction`.

## Canonical Token Bridge Architecture

The token bridge is an application built *on top of* the messaging layer — it's just retryable tickets + L2→L1 messages under the hood.

- **Gateway model:** a **Gateway Router** on each side maps each token to the right gateway. Standard tokens use the **Standard ERC-20 Gateway**; tokens with special needs register a **Custom Gateway**.
- **Deposit (L1 → L2):** the L1 gateway **locks/escrows** your tokens and sends a retryable ticket that tells the L2 gateway to **mint** the bridged version. Fast (minutes).
- **Withdraw (L2 → L1):** the L2 gateway **burns** the bridged tokens and sends an L2→L1 message; after the challenge period you claim on L1 and the escrowed tokens are **released**.
- The bridged L2 token is a distinct contract from the L1 token — "canonical" means this official bridge is the source of truth for the 1:1 backing.

## Challenge Period & UX Implications

The ~7-day challenge period only affects **going up (L2 → L1)** — and it shapes UX a lot:

- **Deposits (down) are fast** (minutes); **withdrawals (up) are slow** (~7 days) because L1 can't trust L2 state until it's confirmed.
- This is why users rarely use the native bridge to exit: **third-party "fast bridges"** (liquidity providers) front you the funds on L1 immediately for a fee, then reclaim through the slow bridge themselves.
- For contract devs: any L2→L1 flow (withdrawals, governance messages) must design around the delay — the message exists immediately but isn't *executable* on L1 until the window passes.
